# MCP reading and server review

The [Hugging Face article by Ksenia Se](https://huggingface.co/blog/Kseniase/mcp), which links to the [full article](https://www.turingpost.com/p/mcp), presents Model Context Protocol (MCP) as a shared way for AI applications to discover and use external data and actions. Without a common protocol, every model and service pair needs custom integration. MCP offers a standard interface for tools, resources, and prompts, so a server can expose capabilities to different AI applications. The article emphasizes dynamic discovery: a client can list a server's capabilities and show their descriptions and argument schemas to the model. This makes tool interfaces and documentation central to reliable agent behavior. It also notes that MCP is an integration layer rather than the agent's planner. The agent still decides when to call a tool and how to interpret its result.

The **host** is the user-facing AI application. In this project, the OpenAI Agents SDK program is the host: it accepts a request, runs the model, and presents the answer. The **client** is the host's MCP connection, here an `MCPServerStdio` instance. It starts the server, discovers tools, sends calls, and returns results. The **server** is the separate FastMCP process that owns the room catalog and reservation database. The host may have multiple clients, each connected to a server. This division keeps the model-facing application independent of the implementation of each external capability. MCP messages carry structured requests and responses across that boundary.

I explored the official [Fetch MCP server](https://github.com/modelcontextprotocol/servers/blob/main/src/fetch/README.md). Its main tool, `fetch`, retrieves a URL and converts content into model-friendly Markdown. The interface documents a required URL and optional output length, starting offset, and raw mode. Chunking with `start_index` makes long pages usable without overloading the model context. The server also exposes a user-initiated prompt, but that is a separate MCP capability rather than another tool. The tool is mostly single-purpose: retrieve and represent web content. Its `raw` flag combines two output representations in one interface, yet both serve the same retrieval task. The documented errors for blocked, unreachable, or invalid URLs make failures visible and predictable. This is stronger design than a general “browse and summarize and save” tool, whose effects and output would be difficult to anticipate. Fetch also illustrates that a tool description, bounded output, and explicit errors matter as much as transport support.
